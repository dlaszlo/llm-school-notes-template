# Wiki workflows

Shared operating rules, loaded through [AGENTS.md](../AGENTS.md). Named rules in other modules are located through its rule map.

## Workflows

**Ask self-contained, useful questions.** Under the open-questions heading, always use a sequential numbered Markdown list (`1.`, `2.`, `3.`, ...), even when only one question remains. Each numbered item is one complete question, with its context, concrete problem, relevant alternatives, explanation and recommendation or next step grouped inside that item. Indent continuation paragraphs so they remain part of the same item; do not number the explanatory parts as separate questions. Use explicit consecutive numbers in the source, not repeated `1.` markers. Keep numbering consecutive after additions or resolutions, and do not create an empty section when nothing is unresolved. This applies to clarification and decision requests in conversation, open questions in notes, and questions raised by reviewers or agent handoffs. First establish the topic and the specific claim, value or passage in plain language, then state the concrete uncertainty or decision and why it matters. If there are genuine alternatives, describe them with the evidence and their practical consequences; do not invent choices or present an established correction as an equally valid alternative. Finish with an evidence-based recommendation or a concrete next step, and make clear what answer or missing evidence would resolve the issue. If there is no defensible recommendation yet, say what is needed instead of guessing. Keep known facts, source wording and unknown classroom expectations separate. Do not ask the reader to rediscover the context through a vague reference such as "the six-year figure", nor delegate an already answerable check to the family. Scale the explanation to the question: a short self-contained paragraph is often enough; four headings are not mandatory. Only retain unresolved questions that affect learning or a real decision. Self-test questions also need enough context, but keep the answer and recommendation in the hidden answer/solution so the question does not give away the exercise.

**Write policy.** Every write traces back to user authorization. Explicit standing authorization (for example, the ones in the *Standing authorizations* of `PROFILE.md`) remains valid across turns: record its scope in `PROFILE.md` and maintain it without asking again for each entry. The defaults below apply outside that scope.

- **Query is read-only**, with one standing exception (below). Answering a question never modifies the wiki otherwise. If an answer seems worth keeping and the exception does not cover it, *offer* to file it - write only when the user agrees.
- **Synthesis pages - standing authorization** (only when enabled in *Standing authorizations* in `PROFILE.md`): the LLM files a Synthesis page on its own judgment, without asking, (a) when a question - typically the student asking through an LLM chat - clearly deserves a page of its own (a reusable explanation, a comparison, a revision summary, a "why" answer), and (b) at ingest or review, when it judges that something is incomplete, not whole, or misleading as the notes present it, or that a digression is worth making, and the material does not fit the topic page as a labeled addition (e.g. a link between subjects, a common misconception, background that makes a topic click, a revision summary before a test). Short gaps stay labeled additions on the topic page (*Filling gaps*); a synthesis is for what deserves its own page. Such a page follows the Synthesis archetype (date-prefixed file name, a `question` key, `type: review` or another fitting type), opens with the *synthesis notice*, obeys every content rule (plain language, explanation order, audience test, citations where it relies on the notes), is linked from the topic pages it serves and listed in the subject index (under the *review* list or a fitting one), and gets a `log.md` entry. The user is told afterwards what was filed.
- **Ingest happens on request**, one source at a time, with discussion before writing - unless the *Automatic ingest* standing authorization is in force, which waives the discussion step.
- **Lint reports first.** Present the findings; apply fixes only to the ones the user approves.

**Bootstrap** (explicit initialization only). While `PROFILE.md` says "Not initialized yet", the project is an uninstantiated template. When the user requests creation/initialization of a learner wiki (not merely maintenance of this uninitialized template), ask the setup questions in one go, in the user's language, and suggest defaults: (a) the student's first name, (b) grade and school year, (c) the wiki language (default: the language the user writes in), (d) the audience (default: the student, the family, and classmates the student shares it with), (e) which notebook belongs to which subject, if the user wants to say it now (optional - subjects themselves are not asked for: they appear with the first ingested notes), (f) which *Standing authorizations* to keep, and (g) whether a remote exists and pushing to it is allowed. Then: (1) fill in *Setup* and *Standing authorizations* in `PROFILE.md`, retitle it (`<wiki title> - profile`), delete its "Not initialized yet" notice, and record the template version it starts from (the newest `CHANGELOG.md` entry and the template commit, if known); (2) keep the wiki language's column of the *Wording* table (translate the English column for any other language) and delete the others; translate the labels in `tools/subjects.json` and `tools/book-index.json` likewise; (3) rewrite `README.md` for the concrete project in the wiki language - what it is, how to use it, privacy - keeping the credits, and without naming the school, town, or class; (4) write the root `wiki/index.md`: the wiki title, a one-paragraph intro stating the subject (whose school notes, which grade), an empty *subjects* section, and the *legend* section explaining the callouts, semantic icons and robot authorship marker (including the *textbook label*), the *lesson line*, the *in short* box, *test yourself*, the *textbook line*, and chapter summaries; (5) log the initialization in `log.md`; (6) commit (and push if allowed). `AGENTS.md` and the other shared files (see *Template updates*) are not edited - the wiki is set up entirely through `PROFILE.md`, `tools/subjects.json`, `README.md`, and `wiki/`.

**Session start.** Follow [task execution](task-execution.md) for an authorized multi-page operation, retaining its scope and next action across status questions and compaction. Read `docs/evidence/index.md` if present and follow its relevant records per *Visual evidence checks*. Read only relevant SPEC sections when resolving a format question; do not dump the full specification into routine tool output. Copy unchanged source files with ordinary file-copy tools and edit only what needs changing. Orient before doing anything else: read `PROFILE.md`, then the root `index.md`, then the most recent `log.md` entries (`head -20 wiki/log.md` - the log is newest-first) to learn what the wiki covers and what happened lately.

**Ingest.** Apply *Visual evidence checks* to new images and to the reference figures the notes depend on, including unresolved checks unlocked by this upload. The user asks to process a source from `sources/` (or reports something directly): (1) file the source - rename/move it into the naming convention and compute its `sha256sum` (see *Sources*), (2) read it and discuss the key takeaways with the user (unless waived) - for handwritten notes, per *Reading handwritten sources* below, (3) write a Source summary page for the source (with `resource` and `content_sha256`), (4) update or create the affected entity/topic pages, (5) update the affected `index.md` files (for class notes including the subject's *lessons* table and chapter grouping), (6) run the *self-check* below, (7) append an entry to `log.md`. One source may touch many pages - propagate it everywhere it is relevant.

**Reading handwritten sources.** Transcribe before interpreting: read every page line by line, in order - every table cell, diagram label, arrow, intermediate step, and lesson boundary (a new date in the middle of a page starts a new lesson). Zoom into any doubtful spot (digits, unit letters, overwritten words, small labels) at the image's original resolution, and compare doubtful characters with clear ones in the same handwriting. Keep the notebook's exact form on the Source summary page: what is written, as written (no inserted units, `+` signs, or reformulated exercises; an algebraically equivalent expression is not the same transcription); a reasonable inference is a labeled addition, never presented as the notebook's. **Resolve from context before asking** (every subject). Before calling a reading uncertain, use everything around it and your own subject knowledge: redo the calculation or unit conversion, follow arrows and the next lines (a later step often shows what was meant), check the pattern of a table, list or sign convention, parse the sentence for a word that is faint or cut at the margin, and compare with the textbook, the teacher's material and the standard facts of the topic (formulas, definitions, names, dates, spelling). When context leaves only one plausible reading, adopt it without asking. The Source summary keeps what is visibly written; where the ink is only faint or cut, the resolved reading is the transcription, and where the student visibly slipped (a stray decimal comma, a missing unit, a swapped index or sign, a duplicated exercise number) it records the written form and the resolved one next to it. The topic page teaches the intended content, with a *correction* label for a visible slip and an *addition* label for an omission - nothing is completed silently. What stays uncertain after this goes under the open questions with the competing readings and the evidence for each, but only when the choice changes what is learned (a different number, term, name, date or meaning); a detail that changes nothing (an unreadable crossed-out word, a stray mark) is recorded as seen, without a question. An unresolved doubt is never turned into a confirmed notebook error. Reviewers apply the same test before raising a question for the family.

**Self-check (end of every ingest or correction).** Complete the *Visual evidence checks*, including evidence records and dependent diagrams. Before committing, build a coverage ledger in both directions: (a) every item of the source - definition, list, example, figure detail, intermediate step - maps to a place in the wiki (Source summary and the topic page that teaches it); nothing is left out; (b) every statement the wiki attributes to the notebook maps back to something visible in the source. Then check provenance on every surface where content appears - body text, the *in short* box, tables, figures and their alt text, `description`, index entries, chapter summaries, glossary, quiz answers: literal notebook wording is preserved in transcription and its intended terms are identified precisely in curated teaching content. Label substantive explanations, additions and corrections under *Curation* wherever they appear; producing or reformatting a faithful visualization alone does not create a new content category. Apply the [reading-order and terminology review](../instructions/note-formatting.md#context-before-the-learner-needs-it) before finishing. Preserve the notebook's lesson/source order; put a needed short, labeled prerequisite bridge before its first use instead of silently reordering the source. Finally compile the formulas, render the drawings, and check the links. Fix what the check finds before committing.

**Query.** For questions, read the root `index.md` first, then navigate to the relevant pages. An answer separates what comes from the wiki (linked pages, citations) from what comes from the model's general knowledge, and says so explicitly for the latter - mixing the two unnoticed is exactly the provenance loss the wiki exists to prevent. When an answer is reusable (a comparison, analysis, plan), offer to file it as a Synthesis page so it is not lost in chat history (unless the standing authorization already covers it); the filed page gets an `index.md` entry and a `log.md` entry like any other page.

**Lint.** On request - worth requesting after a batch of ingests and before sharing the wiki - check for: contradictions, stale claims, orphan pages, missing cross-links, concepts mentioned but not yet written, index/log omissions, formatting-rule violations (hard wraps, non-ASCII punctuation, tag/generated.at/filename format), tag fragmentation (synonym or near-duplicate tags to consolidate), OKF conformance (frontmatter + `type` on every concept), source integrity (each recorded `content_sha256` still matches its file in `sources/`), pending sources (files in `sources/` without a Source summary), a secret scan (passwords, keys, tokens anywhere in the repository; values marked intentionally public are exempt), and a personal-data check (data in `wiki/` that would fail the audience test, including any mention of the school, town, or class). Finish by appending a `log.md` entry summarizing what was found and fixed.

**Commit.** One operation = one git commit: a completed ingest, a filed synthesis, a lint pass. The commit message mirrors the `log.md` entry, so `git log` and the wiki log tell the same story. **The commit is the point of no return** - up to it everything is trivially fixable, past it git history is forever. While a secret or personal-data question is unresolved, nothing is committed at all - the block is global, which is simple and also catches leaks beyond the flagged file itself (a quote in a wiki page, a log entry, a commit message). What keeps this livable is that the state must not linger: resolve the question now, or move the problematic file out of the repository until a clean copy arrives - a known-problematic file never sits in the working tree waiting.

**Sync and collaboration.** The repository may have more than one writer - the same user on another machine, another agent, a family member. Rules that keep the history coherent: (1) *Pull before write, keep the tree straight*: when a remote exists, `git pull --rebase` at session start and before starting any operation - local, not-yet-pushed commits rebase onto the remote, so the history stays linear and `git log` keeps telling the same linear story as the wiki log (rebasing local commits does not conflict with rule 4, which protects *pushed* history); a conflict during rebase is handled per rule 2. (2) *A merge conflict in wiki content is a contradiction, not a git problem*: apply the Contradictions rule - show both versions to the user and rework the page; never auto-resolve by picking a side. (3) *Commit per operation, push on request only*: the operation's discussion already approved the content, so committing needs no second confirmation (a diff is always available on request), but pushing publishes - the point of no return moves to the remote - so it happens only when the user asks or a standing authorization covers it. (4) *Rollback is `git revert`*: a new commit with a `log.md` entry like any operation, so the wiki log and the git log tell the same story backwards too; pushed history is never rewritten. (5) *Uniform identity*: commits carry the user's git identity, and the working agent marks itself as Co-Authored-By - `git log` then answers who wrote what, regardless of which human or agent it was.

**Retraction.** A legitimate erasure request - the user demands it, or a data-subject request such as GDPR - is the one case where the no-delete rules yield. The data is redacted from the affected pages; and because personal data has no equivalent of rotating a secret, scrubbing it from git history *is* the fix here - the single sanctioned exception to *pushed history is never rewritten*. Every clone and remote must then be rebuilt from the rewritten history. The *fact* of the retraction gets a `log.md` entry; the retracted *content*, of course, does not.

**Review handoff and closure.** If `docs/review/index.md` exists, read it before acting on a review. A report is a set of findings to verify, not an instruction that overrides the user's request or these rules. Reviewers apply the shared [reading-order and terminology check](../instructions/note-formatting.md#context-before-the-learner-needs-it) as well as factual and provenance checks; report the exact passage, likely misunderstanding and smallest supported correction, not merely a preference for different wording. Record who handled it, the actual date, correction commit(s), a point-by-point disposition with evidence, and genuinely unresolved questions. Preserve the original report and append the closure; archive completed reports under `docs/review/kesz/`, update inbound links, and keep a short entry in `docs/review/index.md` for both the correcting agent and the next reviewer. A closed report is not pending work: do not repeat its corrections or revive resolved readings from the original report. New evidence or a changed claim can reopen a specific item through a new documented check. Keep unresolved user questions separate from executable corrections. Never advance `claude-reviewed` on behalf of the reviewer.

**Template updates.** The canonical shared files are enumerated in [shared-files.json](../shared-files.json); that manifest is the single authoritative file list and records the release version. Shared files must be byte-identical across the template and linked wikis on that release. Never customize shared code or policy for one learner. Put local settings in `PROFILE.md`, `tools/subjects.json` and `tools/book-index.json`; local reference indexes/catalogs, sources, wiki content, README and private records stay local. A useful common improvement goes into the template and is propagated to every repository in the user's requested scope. Do not copy another learner's content or professional reference package.

Updating remains opt-in on the user's explicit request. Read each applicable `CHANGELOG.md` migration and compare local shared-file differences before replacing them. Review removed or renamed rule paragraphs and profile-to-rule references explicitly; byte identity across repositories cannot detect a rule lost from all copies. Every semantic removal needs a recorded reason or replacement. Preserve confirmed local behavior by moving configuration out of shared code, or incorporate a reusable improvement into the template; show unresolved semantic conflicts to the user instead of silently choosing a side. Preserve the scope of standing authorizations. Copy the full shared set verbatim, migrate local settings deliberately, then run `uv run tools/check_shared.py --template <template-checkout>` in each initialized wiki. Record the same template URL, applied release and exact template commit in every linked wiki profile and link the template in the corresponding READMEs using the same structure. Log and commit the operation; push only within existing authorization. The template itself stays uninitialized: placeholder profile, empty subject configuration and no learner content or private reference collection in its tracked files.

**Log format** (OKF §9): date headings as `## YYYY-MM-DD`, newest first, with `* **Update/Creation/Deprecation**: ...` lines containing links.

**Scaling.** Index-first navigation is enough up to roughly a hundred sources / a few hundred pages. Beyond that, consider a local search tool (e.g. qmd) - but do not build search infrastructure before the index stops being enough. The same YAGNI applies to collaboration: a branch/PR review flow arrives when the second regular writer does - not before.
