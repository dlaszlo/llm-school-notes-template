# Sources and evidence

Shared operating rules, loaded through [AGENTS.md](../AGENTS.md). Named rules in other modules are located through its rule map.

## Sources

- **Naming**: one file per source, `YYYY-MM-DD-short-title.<ext>`, where the date is the acquisition date. A source that is inherently multiple files gets a directory with the same naming (`YYYY-MM-DD-short-title/`). Obsidian-managed attachments live in `sources/assets/`.
- **The user drops files in under any name; the LLM files them.** Renaming and moving a source into the convention is the first step of ingest. The only writes ever allowed in `sources/` are *acquisition* operations: filing (rename/move) and materializing a URL source (below). Content of existing files is immutable: never edit, never delete. (Parking a flagged, not-yet-committed file out of the repository per the commit gate is an acquisition-stage move, not a deletion - immutability protects what has been ingested.)
- **A URL is a pointer, not a source** - `sources/` must stay complete to be the source of truth. When the user gives only a URL, materialize it at ingest: fetch the content with whatever the environment offers and save it into `sources/` under the naming convention, then ingest from the local copy. `resource` keeps the original URL; `content_sha256` covers the saved copy. Prefer a readable markdown extraction over raw HTML when materializing web pages - the hash covers whichever copy was actually read. If the environment cannot fetch (many sites block non-browser clients), ask the user to save the page from their own browser (e.g. with a web clipper) and drop it in - never ingest from a URL without a local copy.
- **Images**: acquired third-party images go in dated files under `sources/assets/` and remain private working copies. Do not embed images copied or extracted from teacher materials in the wiki; apply *Images from material to learn* below. Independently acquired reusable images require the rights and attribution checks in that section. Our own wiki images go in `wiki/assets/`. Use relative image links, meaningful alt text, and a prose account of what the image establishes. Read images before describing them. Choose authored structure, precise code or generated illustration by the learning task under *Choosing and replacing authored visuals*.
- **Link original teaching files**: when an ingested teacher-supplied material has an original PPTX, PDF, DOCX or similar file, add a visible relative Markdown link near the beginning of its Source summary / lesson-notes page, labeled in the wiki language as original teaching material with the file format. Link to the actual original (including an `original/` subdirectory when present), not only to `document.md`; a frontmatter `source_file` value is not a reader-facing link. Preserve the original filename, use angle brackets around a link destination containing spaces, and verify that the file exists. Topic pages can link to this summary instead of duplicating the download link. This is for the intended private audience and does not apply to notebook photos; public exports omit raw-source links under the existing publication rules.
- **Processing status**: a date prefix records filing, not proof of ingestion; users may upload already-dated directories. The authoritative record is the wiki itself - every ingested source has a Source summary page and a `log.md` entry. Treat an uploaded file as pending until those records exist, and check hashes to avoid duplicate ingestion. A static `sources/README.md` explains this to humans; it is the only non-source file allowed there and is never treated as a source. `sources/` holds only material meant to be ingested. Context-only material - something shared for a discussion or a one-off task, not for the wiki - lives in the conversation or outside the repository: every file in `sources/` carries a processing status, so a context file would sit as "pending" forever and lint would keep reporting it. When discussion reveals that a dropped file is context rather than source, it leaves the repository - an acquisition-stage move like parking; nothing was committed.
- **Notebook photos are internal only**: the student's and classmates' notebook photos - classmates lend their notes to each other for learning, but nobody wants their incomplete, messy notebook shown around - stay in `sources/` and are never published or shown raw to anyone outside the family; only the distilled wiki pages may ever be shared. **Public version**: public publication requires its own user authorization; a private Git push does not grant it. Produce a filtered derivative from the canonical private Markdown rather than rewriting the teaching notes for publication. Omit school, town, class, private individuals, raw notebook images, raw-source listings, copied textbook/teacher files and restricted assets. Only an explicitly authorized owner's first name may remain. A specific private-source citation may be retained only with explicit authorization as an access-controlled destination (for example a private GitHub file); verify its access boundary, use neutral link text, and never expose signed/token-bearing URLs, private filenames or collection listings. A restricted link does not authorize public embedding of its content. Preserve ordinary bibliographic citations. Without that authorization, omit raw-source links. These are export requirements, not a claim that a public exporter is installed. A classmate's notebook is ingested like the student's own (e.g. when the student was ill), without naming the classmate in `wiki/`.
- **Catch-up material**: when the student missed lessons and brings in a classmate's notebook, the material must be visibly marked as something to catch up on: the lesson-notes page gets `notebook: classmate` and `catch_up: open` in its frontmatter; right after the header it opens with `> [!IMPORTANT]` + the *catch-up notice*; its banner says "catch-up notes" (`tools/banner.py` reads `catch_up`); its rows in the subject's *lessons* table start with 🤒; and the subject index lists it under the *catch-up* section right after the back link, above the table. When the student says they have caught up (or their own notebook page for those lessons arrives), set `catch_up: done`, drop it from the catch-up list, and turn the row mark into ✅; the page keeps `notebook: classmate`. The classmate is never named, and their own solutions, grades, and teacher remarks are left out.
- **Teacher materials**: besides the notebook, a teacher sometimes shares material with the class - slides (pptx), a pdf, a docx, or a photo of a printed handout. The notebook is always material to learn; a teacher's material is one of two kinds, and the student says which when sending it, with one word: *to learn* (lesson slides, an outline, a worksheet, a summary for a test - often shared because the class did not write it down) or *background* (a longer reading, a scanned book chapter, optional material). When the word is missing, **ask before ingesting** - even under the *Automatic ingest* authorization - and offer your own guess with its reason (e.g. "a 6-slide lesson deck on sets - I would treat it as material to learn; shall I?"); ingest only after the answer. *To learn*: a source like the notebook - it goes to `sources/` under the naming convention with its hash, gets a Source summary (what the material contains, the lesson date it belongs to), and its content goes into the topic pages like notebook content: with the *lesson line* and a keyed footnote to the material (slide or page number), no label. Where the notebook and the material differ, flag both per *Contradictions*. *Background*: a reference, not a source - it goes to `references/<subject>/<id>/` (converted, with its `index.md` map, per *References*), and what comes over from it is labeled with the *background label*, like the *textbook label*. Either way the material is the teacher's work: it enters the wiki in our own words only - no verbatim text, no copied slides - and the teacher's name, the school, and the class never appear. **Images from material to learn**: apply the no-copy rule and learning-preserving replacement workflow in *Images from material to learn* below; being assigned for learning does not grant image redistribution rights. Reading: pptx with `python-pptx` plus each slide rendered as an image (figures carry meaning); docx with `python-docx` plus its images; a text pdf directly, a scanned one page by page as images; a photo like a notebook photo (*Reading handwritten sources*). Conversions are ephemeral. **Pre-converted material**: the user may upload a teacher's material already converted, as one multi-file source - a directory in `sources/` holding the original file (pptx, docx, pdf), its `document.md`, and a `figures/` folder - and then ask for the ingest. This is the one other exception to ephemeral conversions: the conversion stays next to the original. File the directory under the naming convention (`YYYY-MM-DD-short-title/`) if it is not yet, record `content_sha256` of the original file (the authoritative source) and of `document.md` in the Source summary, and ingest from `document.md` and its figures; where the conversion looks doubtful (a formula, a slide's order, a missing diagram), the original decides. Figures follow *Visual evidence checks*: inspect each image that the current material depends on, including task-referenced images without a description; the images are not photos, so they are never re-encoded with `tools/prepare_photo.py`.
- **Reference material is not a source**: textbooks and similar works the user hands over are not ingested and never go into `sources/`. A converted book lives in `references/` (see *References* below); photographed textbook pages shown only for checking are used the same way but not kept (see *Requesting a page* under *References*). The student's notes remain the only thing the wiki pages are built from.
- **Append-only versioning**: a newer version of an already-ingested source is a new dated file, never an overwrite. Its Source summary links back to the old one; the old summary gets `status: deprecated` and a link to its successor. No old-versions folder - nothing is ever replaced, and git keeps history anyway.
- **Provenance and attribution**: the Source summary always records where the source came from - original URL, author/publication, acquisition date. When the source lives in git hosting, prefer the commit-pinned URL (gist revision, `raw.githubusercontent.com/<owner>/<repo>/<commit>/...`) over a branch URL - it identifies the exact version forever. Downloaded material in `sources/` is a private working copy and must never be republished; if this repository is ever made public, exclude `sources/` or clear its licenses first. The wiki layer (own words plus citations) is the shareable part.
- **Non-markdown formats** (PDF, DOCX, images, spreadsheets, ...): sources stay in their original format - that is the authoritative copy. At ingest, read what you can natively (agents typically read PDF, images, and plain text directly); for formats you cannot read, use whatever conversion tool the environment happens to offer, and if there is none, ask the user to either install one or re-export the document in a readable format. The template mandates no tool. Conversions are ephemeral - never store derived copies in `sources/`, because they drift from the original and only the distilled knowledge (the wiki pages) needs to persist.
- **Audio and video**: retain the recording and its platform transcript as one dated multi-file source. If absent, obtain a transcript using available tools, or ask the user. Store an expensive transcription as an explicit exception to ephemeral conversions. Hash the transcript that was actually read; cite exact passages. Never pretend to have inspected a recording when only its transcript was available.
- **Large binaries and license-cautious sources** may remain local and gitignored. Retain the source summary, original resource, and content hash in history. Confirm redistribution rights before publishing raw copies.
- **Tools**: the scripts in `tools/` are run with `uv run tools/<name>.py ...`, which creates the project's Python environment from `pyproject.toml` and `uv.lock` on first use - no `pip install`, no `sudo apt`, no system Python packages. A new dependency is added with `uv add <package>` and committed together with the updated `pyproject.toml` and `uv.lock`; the `.venv/` folder is never committed.
- **Photos are filed with `tools/prepare_photo.py`**: every photo (notebook page, handout, board) is stored in `sources/` with `uv run tools/prepare_photo.py <incoming image> <target in sources/>`, never copied as it arrived. The script keeps the resolution, turns the image upright, re-encodes it as JPEG quality 90 (visually identical at 100% zoom, a fraction of a phone JPEG's size), drops all metadata (GPS position, device, date), and prints the hash. The stored copy is the source: ingest reads it, the nightly review checks against it, and `content_sha256` records it; the incoming original is not kept. A photo already in `sources/` is never re-encoded (its hash is recorded).
- **Integrity hash**: at ingest, compute `sha256sum` of the source file and record it in the Source summary frontmatter as `content_sha256`. URLs rot; the hash permanently identifies exactly what was read, and lets anyone verify the copy is untouched. When the original is a web page, also request a Wayback Machine snapshot (`https://web.archive.org/save/<url>`) and record the snapshot URL in the Source summary frontmatter as `archived`; if archiving fails, note it under the *open questions* heading and move on. Never inject metadata into the source file itself - provenance lives in the Source summary. (Exception: the project-root documents `SPEC.md` and `llm-wiki.md` carry their own frontmatter, with `content_sha256` covering the verbatim body after the frontmatter block.)

## References

`references/` holds reference works - typically textbooks converted into an LLM-friendly form (text, image descriptions, provenance) - that the user provides. The notes are built from the student's notebook; the books are for checking, completing, and citing. They are not ours and not sources: they are never ingested, get no Source summary, and - like `sources/` - are a private working copy that is never shared or published.

- **Layout**: `references/<subject>/<book-id>/`, each with a `README.md` (bibliographic data, how the page numbers map, the lesson table, hashes, what is generated), `document.md`, `provenance.json`, and a generated `index.md` (see *Reading a book*). `references/README.md` explains the layer to humans.
- **Reading a book**: never load a whole `document.md` - a book is hundreds of thousands of tokens. Read the book's `index.md` first: it maps every lesson and every printed page to a line range of `document.md`, and points to the book's own table of contents, indexes, glossary, and answer key. Then open only the lines needed (`read_file` with offset and limit, or `sed -n 'FROM,TOp'`), and search for a term inside that range. The `index.md` is generated by `uv run tools/book_index.py references/<subject>/<book-id>` from the page anchors of `document.md` and the book's own table of contents (the README's lesson table fills the gaps; the printed-page offset comes from the README); it is never edited by hand - fix the README table or the script and run it again. Run it whenever a book is added or replaced, and commit `index.md` with the book. **Book figures** are checked automatically when the current notes depend on them, following *Visual evidence checks*. Follow a specific passage, caption or exercise reference in `document.md`, including an undescribed image that the exercise asks the reader to interpret. Converter descriptions are navigation aids, not substitutes for viewing available images. Missing or incomplete images leave the affected question open until the necessary page is available. An *index-only* book has no `document.md`: its `README.md` is the map.
- **Index-only books**: a book that may not be converted - its publisher forbids processing it with AI systems, or no usable copy exists - gets only a hand-made index: its `README.md` holds the bibliographic data, the reason, the table of contents (section number, title, start page), and, where the book has one, its subject index (term, page) - numbers and titles only, no text from the book; there is no `document.md` or `provenance.json`. Topic pages take their *textbook line* from the index; where the section is chosen by topic rather than from a reference written in the notebook, the line ends with the *index-based note*. Checking the notes then relies on subject knowledge (recalculation, units, standard definitions) with the usual labels, plus *Requesting a page* where that is not enough.
- **What they are for**: (1) *accurate ingest* - check readings, names, dates, and terms in the student's notes against the book; (2) *filling gaps* - complete incomplete notes up to the lesson's scope, per *Filling gaps*; (3) *textbook references* - give topic pages a pointer to the lesson and printed pages, so the student can look it up; (4) *synthesis* - write Synthesis pages from the book only where they connect to the notes, and in moderation.
- **How facts come over**: in our own words only - never publish any text or image from the book: no verbatim passages or quotations, no copied or traced figures; our own drawings and syntheses based on it are fine. Book content is cited - a `sources` entry pointing at the book's `document.md`, and keyed footnotes with the **printed** page number (the book's README says how PDF pages map to printed ones) - and, so the student always sees what was taught in class and what only the book adds, **anything on a topic page that comes only from the book (not in the notebook or teacher-supplied material to learn) is visibly labeled** with the *textbook label* (a `> [!NOTE]` callout, or inline with its emoji where a callout cannot go, including in the *in short* box and chapter summaries). Where the book merely confirms or pinpoints something that is in the notebook or teacher-supplied material to learn (a page reference, a checked result), a footnote is enough, no label. Image descriptions in the conversion are machine-generated - use them to understand a figure, but cite only the book's own text, captions, and labels. General knowledge beyond the book still carries the usual labels.
- **Requesting a page**: when understanding the notes or settling a doubtful reading needs a page of a book that is not converted in `references/` (an index-only book, or a book the user has not handed over) - the notebook relies on an example, figure, exercise, or notation of the book that cannot be understood or checked without it - say so in the report and name exactly which page is needed (from the index where there is one, e.g. `1.3.1, p. 10 - for the notation of the notebook's figure 2`); until the photo arrives, the question stays under the *open questions* heading. Ask rarely and precisely: subject knowledge settles most things. The photo that arrives is **not a source**: it is used only for this check, never copied into the repository, and its chat message is deleted once the check is done, where the channel allows it. What comes over from it follows *How facts come over*: our own words, the printed page number, and the *textbook label*.
- **Contradictions**: when the notes and the book disagree, flag both per the Contradictions rule and tell the user - the class may have said something the book does not.
- **Topic pages** name their textbook lesson near the top (the *textbook line*), or say the book does not cover the topic.

## Visual evidence checks

This workflow applies to every agent (including Groot/Hermes, Claude Code, Codex and scheduled reviewers). It is a required part of an authorized ingest, correction or review, not an optional extra requiring another request. It does not authorize unrelated ingestion, publication or changes during a read-only query.

* **Inspect available evidence.** Read every newly supplied notebook/source image directly. For the relevant reference pages, follow the book index and the selected `document.md` passages, and identify each image on which a note, exercise, explanation or authored diagram depends. Open those images when available, even if OCR or an earlier model's description sounds certain. A task referring to pictures is enough reason to inspect its referenced images; a missing description or a converter's "decorative" classification does not establish that they are decoration. Do not catalogue unrelated image folders.
* **Use conversion metadata as diagnostics.** If supplied, read the relevant `manifest.json` and `provenance.json`: check source identity/hash, run/version, page coverage, missing assets, validation warnings and the specific figure's crop-edge flags. A `content_at_edge` flag signals possible truncation, not proof; `clear`, `complete` or `operation_verified` does not certify visual or factual accuracy. Use stable element IDs and page identifiers, not stale line numbers alone. On a user-supplied conversion update, compare changed elements with the notes, refresh recorded hashes and regenerate navigation indexes; inspect newly relevant images, preserve the supplied files verbatim and record which version was checked. Do not copy new machine descriptions into notes without checking them.
* **Check the crop before the claim.** Document converters can truncate, misassign or combine figures. Check borders, labels, arrowheads, legends, scale, exercise number and surrounding text. Zoom the original-resolution image; a larger display does not recover missing detail. When a needed part or its context is missing or ambiguous, inspect the original full page/PDF if available. Otherwise record the exact page/detail needed and leave that claim unresolved; do not invent the missing part or treat a crop as proof that something was absent from the page. An index-only reference remains index-only.
* **Preserve the learning source's image order.** When notes are based on a notebook that gives an image/answer order, follow that order: it records the student's own lesson sequence and may reflect a deliberate choice. Otherwise accept the textbook image-reference order in `document.md`, using `provenance.json` when available to locate the same sequence; these references record textbook order. If no notebook order is available, the image-reference order recorded in the processed textbook is authoritative for ordering the notes. Accept it without requiring independent reconstruction of the original page layout; the mere possibility of a conversion error is not grounds to question this order. Do not substitute directory listing or filename order. Different left-to-right or top-to-bottom reading of a page layout is not, by itself, an error: do not reorder notebook answers, flag them as wrong, or require a full-page upload solely because their order differs from the textbook references. Match the scenes by content when needed. This ordering rule does not override a demonstrated factual error; investigate such errors under the normal evidence and correction rules.
* **Separate observation from interpretation.** Record what is visible separately from its interpretation, the converter's text and the notebook's answer. A textbook can clarify the task, but cannot prove illegible handwriting. Check directions, connections, shaded regions and labels explicitly. For our own diagrams, compare every meaningful element with the supporting evidence, then render and inspect the final drawing. Keep source images, converted `document.md` and provenance files unchanged; correct the wiki and the verification record, not the acquired evidence.
* **Preserve the check for the next agent.** For image-dependent claims, write a focused, private record in `docs/evidence/YYYY-MM-DD-<topic>.md`, outside the learner-facing wiki. Include the actual verifier and timestamp, affected wiki sections/assets, relative paths and SHA-256 hashes of the images actually inspected and the conversion used, printed/PDF page and figure/exercise identifiers, the locating `document.md` element ID, any crop coordinates, observed details, interpretation, decision (changed/confirmed/unresolved) and remaining limitations. For an unavailable full page say so; do not claim a complete-page check. Link earlier records when revisiting a claim. These records are check notes, not a new image catalogue or a replacement source, and follow the repository's privacy rules.
* **Make evidence discoverable.** On the first actual check create `docs/evidence/index.md`; keep it as a compact mapping from affected wiki pages/reference figures to the relevant record anchors, including unresolved checks. At session start, and before changing or reviewing an image-dependent claim, read that index if it exists and the relevant records. Maintain it in the same operation as the note changes. Do not create an empty index in unused templates.
* **Revisit on new uploads.** When an authorized upload supplies a missing image, a fuller page or a new version, match it to these unresolved checks and affected notes; perform the check automatically and propagate confirmed changes to text, figures, alt text, summaries and quiz answers. A hash identifies the inspected version, not truth. A changed image, conversion, dependent claim or interpretation requires a fresh check; a previous agent's conclusion is not authority. Before recording a contradiction between a new source and an earlier notebook reading, reopen the relevant existing notebook photo as well as the new evidence. A conflict with our transcription is not yet a conflict between sources.
* **Review with the same evidence.** Scheduled and interactive reviewers read the relevant records, inspect the same image/region and compare the current hashes before proposing a visual correction. If the image cannot be accessed, or the crop does not settle it, report an unverified question with the missing evidence instead of an asserted error. If direct observations disagree, record both readings and precise locations; do not silently overwrite one with a model-generated description. Before committing a correction, verify record links/hashes and consistency across every affected learner-facing surface. Record unresolved points honestly; never mark the whole page verified from a partial image check.

### Images from material to learn

* **Do not embed teacher-material images.** Do not copy, crop, screenshot, trace, hotlink or generatively restyle images from teacher slides, handouts, classroom uploads or textbooks into `wiki/`, websites, PDFs or other learner-facing derivatives. This also applies to private wiki pages, so later publication cannot accidentally expose them. Original acquired evidence remains unchanged and private in `sources/` or `references/`; archive and evidence records are not deleted or rewritten. This rule replaces the former exception for selected class-material images in `wiki/assets/orai/`.
* **Preserve the learning purpose.** Inspect relevant source images under *Visual evidence checks*. Identify what must be learned, then create an independent explanatory visual from verified facts using the appropriate precise or illustrative tool. Do not use a prohibited image as an image-generation/editing input, trace its composition, or treat changing style as clearing its rights. Preserve required instructional content and exact relationships without copying distinctive artwork. A generated scene must not masquerade as a historical photograph, artwork, archaeological finding or official symbol.
* **Use authentic reusable images when recognition matters.** For an actual artwork, object, place or prescribed sign, prefer a verified reusable original from its authoritative source or Wikimedia Commons over a fabricated substitute. Acquire it independently from that source, never from the teacher's file. Check the individual file's creator, original source, exact license/version or documented public-domain basis and relevant restrictions; appearing on Wikipedia, in a search result or in a slide is not permission. CC0/public-domain, CC BY and CC BY-SA are useful candidates, not automatic approvals. For BY-SA adaptations retain the required same/compatible license; this does not automatically relicense unrelated page text. Other licenses need an explicit compatibility check for the intended web, print and downloadable uses. If permission cannot be established, use an independent explanatory diagram or a source link and state any remaining learning limitation. Do not invent a recognizable historical object or redraw a regulated pictogram as a substitute.
* **Keep attribution visible and portable.** Put reusable third-party images under `wiki/assets/` with meaningful alt text and a concise image credit or keyed credit footnote: creator, work/source link, exact license with link, and material changes made (such as cropping or altered content), where required by the license. Keep routine resizing, file-format conversion and compression details in private provenance or an HTML comment, not in learner-facing captions; these technical steps alone do not add teaching value. Preserve supplied notices where required. Carry these credits into the website, printable version and downloaded media; an HTML comment alone is insufficient. Keep the acquisition date, file SHA-256, inspected license evidence and original URL in the existing private evidence record, linked from its index. An image caption must describe the replacement actually shown, not an absent slide image.
* **Replace existing embeds completely.** Find every embed, full-size link, caption, image-dependent explanation, question and answer using a prohibited copy. Replace it with a checked independent visual or independently acquired reusable image and update those dependencies together; preserve factual citations to the lesson. Do not leave a question requiring an image that the learner cannot see. Remove obsolete publication assets only after a repository-wide reference check; preserve acquired sources and historical evidence privately. Record the old-to-new mapping and verified hashes in the existing evidence system. Reviewers check origin and rights separately from visual/factual correctness. A copied file is still prohibited after renaming; a filename scan is only a backstop.
* **Do not promise rights we do not hold.** A site-wide reuse license covers only rights the publisher can grant. Identify third-party exceptions and their own licenses. AI generation is not proof of originality or copyright ownership; do not apply a blanket claim to protected source expression or third-party components. Choosing the site's own content license is a separate owner decision, not implied by accepting a CC-licensed image.
